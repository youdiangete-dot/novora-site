# NOVORA Agent 53B AI Sketch Pipeline Implementation Boundary Review

## Purpose And Role

Agent 53B is a docs-only boundary review before any future implementation of
the internal AI sketch draft pipeline.

This document defines what future work may do only after separate approval,
what must remain blocked, what is deferred from the MVP, and what must be true
before any code-level implementation begins.

Agent 53B is:

- Internal planning only.
- A documentation boundary review.
- A safety and scope contract for future implementation agents.
- A review layer after Agent 50A, Agent 50B, Agent 50C, and Agent 53A.

Agent 53B is not:

- Implementation.
- An API route.
- A server action.
- Image generation.
- OpenAI or image-provider integration.
- SQL.
- Supabase live work.
- Storage work.
- Customer-facing UI.
- Email delivery.
- CAD, a quote, an order, or production approval.

No image is generated by Agent 53B. No OpenAI, image provider, Supabase live
schema, live rows, storage bucket, email provider, plugin, MCP server, Codex
setting, or third-party service is connected or changed.

## Relationship To Prior Agents

The locked planning chain remains:

```text
Customer Concept Brief
-> Design Spec JSON Schema v1
-> Hand Sketch Instruction Template v1
-> Concept Brief to Design Spec transformation plan
-> Internal AI sketch draft pipeline plan
-> future implementation, only after separately approved boundary review
```

Agent 50A defines Design Spec JSON Schema v1.

Agent 50B defines Hand Sketch Instruction Template v1.

Agent 50C defines Concept Brief to Design Spec transformation planning.

Agent 53A defines future internal AI sketch draft pipeline planning.

Agent 53B reviews the safe implementation boundaries before future code work.
It does not replace or implement Agent 50A, Agent 50B, Agent 50C, or Agent 53A,
and it does not start any future implementation agent.

## Future Implementation Boundary Overview

Future implementation areas must be classified before work begins:

| Future area | Boundary classification |
| --- | --- |
| Pure mapping/helper code | Allowed in a future low-risk code agent |
| Local fake test fixtures | Allowed in a future low-risk code agent |
| Schema validation | Allowed in a future low-risk code agent when fake/local only |
| Internal job orchestration | Requires separate planning first |
| Admin-only pipeline controls | Requires separate planning first |
| Provider integration | Requires separate planning, env/secrets approval, and cost/security review |
| Storage/database writes | Requires separate SQL/storage approval |
| Email delivery | Requires separate customer-delivery planning and approval |
| Customer-facing display | Deferred from MVP unless separately redesigned and approved |
| Gallery approval | Forbidden for MVP; separate future consent system only |

Future work must preserve the locked MVP AI sketch rules:

- Customer submits a Concept Brief before sketch workflow begins.
- GPT or an image model can generate internal drafts only.
- GPT may assist revision prompts or redraw direction only inside an internal
  workflow.
- Human review is required.
- Human final approval is required.
- Customer only sees the human-reviewed version.
- Unreviewed AI or GPT drafts must never be shown or delivered to customers.
- AI sketch is concept sketch only, not CAD, quote, order, or production
  approval.
- `approved_for_customer` is not equal to `approved_for_gallery`.
- AI generation success alone must not approve a sketch.
- Customer-facing sketch delivery remains email-only after human review,
  optimization, and approval.
- Customer pages must not display unreviewed AI sketches.

The only legal final AI sketch review statuses remain:

- `internal_draft_not_generated`
- `draft_generated_internal_only`
- `needs_revision`
- `approved_for_customer`

`pending` is illegal, excluded, and not valid.

## Future Low-Risk Code Boundary

A future first code-level agent may be considered low risk only if separately
approved and limited to pure local behavior.

Potentially safe future helper scope:

- Design Spec validation helper.
- Hand Sketch Instruction formatting helper.
- Internal prompt policy assembler using fake fixtures.
- Internal-only status type guard.
- Local fake fixture tests only.

That future low-risk code agent must not:

- Read from or write to live Supabase.
- Call OpenAI or any image-generation service.
- Require env vars or secrets.
- Generate images.
- Add customer-facing UI.
- Send email.
- Upload to storage.
- Mutate production data.
- Use paid provider features.

Agent 53B itself does not implement these helpers.

## API And Server Action Boundary

Future API route or server action work is not allowed until a separate task
explicitly approves it.

Before future API or server action work begins, the plan must define:

- Explicit user approval for API or server work.
- Admin-only access boundary.
- No public anonymous trigger.
- Rate-limit and abuse guard review.
- Idempotency key strategy.
- Duplicate job prevention.
- Failure handling and retry boundaries.
- Logging boundaries that exclude secrets, prompts with private data, and
  customer-sensitive notes.
- No customer-facing sketch exposure.
- No automatic approval.
- No automatic email.
- No gallery approval shortcut.

Agent 53B does not create API routes or server actions.

## Database, Supabase, And Storage Boundary

Future database, Supabase, or storage work requires separate approval.

Possible future planning areas include:

- Internal generation job tables.
- Internal draft output metadata.
- Internal-only storage bucket usage.
- RLS and storage policy review.
- Idempotency keys.
- Duplicate prevention.
- Audit fields.
- Admin-only access.
- No customer-facing public URLs.
- No protected reference URL exposure.

Future database/storage work must preserve that internal draft outputs are not
customer-deliverable until human review and a separate delivery workflow approve
them.

Agent 53B does not:

- Execute SQL.
- Inspect live Supabase schema.
- Inspect live rows or customer data.
- Create buckets.
- Modify RLS, grants, policies, migrations, storage, or buckets.
- Upload images.
- Read or write protected customer data.

- Model and provider selection review.
- Cost controls.
- Retry cap.
- Idempotency key.
- Internal-only generation flag.
- Human pre-generation gate.
- Human post-generation review.
- No automatic customer delivery.
- No generation-success approval.
- No customer-facing output.
- No gallery approval.

Agent 53B does not:

- Call OpenAI.
- Call image generation.
- Generate images.
- Require API keys.
- Connect third-party provider services.

## Human Review Gate Boundary

Every future AI sketch pipeline must include these human gates:

- Pre-generation review of Design Spec JSON.
- Pre-generation review of Hand Sketch Instruction.
- Post-generation internal draft review.
- Revision or redraw decision.
- Final approval for customer delivery.
- Separate future gallery approval if gallery use is ever added.
- Manual fallback if automation fails.

No AI draft can bypass human review. No customer sees an unreviewed draft.
`approved_for_customer` is not gallery approval. Generation success is not
approval.

## Customer Delivery Boundary

Customer delivery remains email-only after human review, optimization, and
approval.

Future work must not add:

- Automatic email from generation success.
- Public sketch URL.
- Customer-facing preview page.
- `/design/sketch` customer delivery path unless separately redesigned and
  approved.
- Website gallery approval shortcut.
- Customer account requirement in the MVP.

Agent 53B does not create customer delivery behavior.

## Admin UI Boundary

Possible future admin-only UI areas may include:

- Internal job status.
- Draft output list.
- Failed job status.
- Regenerate or revision request.
- Approve for customer.
- Mark needs revision.
- Cost estimate visibility.
- Prompt and template version visibility.

Future admin UI work must remain admin-only and must not expose internal drafts
to customer pages.

Agent 53B does not implement UI and does not change any admin write path.

## Security And Privacy Boundary

Future implementation must protect customer and internal data.

Required boundaries:

- No private customer contact data in prompts.
- No real customer data in examples.
- No `reviewer_note`.
- No `customer_safe_note`.
- No live customer data inspection.
- No secrets in docs, logs, prompts, fixtures, or examples.
- No protected reference image URLs exposed.
- No third-party service connection without separate approval.
- No analytics, tracking, marketing, CRM, chat, payment, account, booking, or
  monitoring integration in this workstream.

Reference images remain inspiration-only unless a separate provider-boundary,
privacy, copy-risk, and storage review approves a different handling path.

## Failure And Risk Boundary

Future implementation must handle these risks before runtime work begins:

- Invalid Design Spec.
- Invalid Hand Sketch Instruction.
- Unsupported material.
- Unsupported piece type.
- Risky reference image copying request.
- Unsafe image output.
- Structurally unusable sketch.
- Provider timeout or failure.
- Duplicate generation attempt.
- Excessive retry or cost.
- Missing admin approval.
- Accidental customer exposure.
- Accidental gallery approval.
- Accidental CAD, quote, order, or production implication.

Failure must keep the Concept Brief intact, keep unreviewed drafts internal, and
route the work back to human review or manual fallback.
